("hubsell website"). Live container version: 45, "Update cookie firing". The

## The headline finding

`src/scripts/track.ts` pushes `cta_click`, `form_start`, `form_error`, and
`form_submit_success` into `dataLayer`. **None of the four are wired up in GTM.**
There is no Custom Event trigger and no GA4 event tag for any of them. The pushes
happen in the browser and go nowhere — GA4 never receives them. This means:

- `form_submit_success`, the completion event CLAUDE.md names as the actual
  conversion signal, is not reaching GA4.
- `form_error` (the corporate-email-gate / Turnstile rejection signal) is not
  reaching GA4 either.
- `cta_click` and `form_start`, the funnel steps before conversion, are not
  reaching GA4.

The only GA4-facing tag in the container is the base **Google Tag** config tag
(`G-5NPVYW5V3R`, tag 49), which only sends what GA4's automatic/enhanced
measurement covers (page_view, scroll, outbound click, etc.) — not custom
dataLayer events. So any GA4 report built on `cta_click` or `form_submit_success`
as event names will come back empty, and the "conversion" GA4 currently sees (if
any) is whatever enhanced measurement infers, not the actual form completion.

## Dead / orphaned triggers

Two of the three triggers in the container are defined but attached to **no tag
at all**:

- **"Window load"** (trigger 41) — unused.
- **"Form Submission - Book a Call"** (trigger 55) — a native GTM Form Submission
  trigger matching `{{Form ID}} == "wf-form-Book-a-call"`. That ID is a
  Webflow-generated form ID from before the Astro rebuild. The current
  `BookCallForm` component (Astro/React, POSTing to `/api/subscribe`) does not
  render a form with that ID, so this trigger would not fire even if it were
  attached to something. It's leftover Webflow-era configuration.

Only **"BLOCK - non-production hostname"** (trigger 60) is actually in use, as a
blocking trigger.

## What this means for CLAUDE.md's analysis guidance

The doc's instruction to judge pages by "corporate-email conversion" and to treat
`form_submit_success` as the completion event assumes GA4 is receiving that event.
It currently is not. Any GA4 report pulled today that references `cta_click`,
`form_start`, `form_error`, or `form_submit_success` as GA4 event names will return
no rows — that's a GTM gap, not a traffic or content problem, and should not be
read as "nobody converts."

## Fix built — 2026-09-05, in the default workspace, not yet published

Built directly in workspace `60` (the live container is still version 45; nothing
below is production until a version is created and published):

**5 Data Layer Variables** (ids 61-65): `DLV - cta_destination`, `DLV -
cta_location`, `DLV - cta_text`, `DLV - form_id`, `DLV - form_error_field`. Each
reads the matching key straight off the dataLayer push in `track.ts`.

**4 Custom Event triggers** (ids 66-69): `CE - cta_click`, `CE - form_start`,
`CE - form_error`, `CE - form_submit_success`, each matching `{{_event}}` equals
the literal event name.

**4 GA4 Event tags** (ids 70-73): `GA4 - cta_click`, `GA4 - form_start`,
`GA4 - form_error`, `GA4 - form_submit_success`. Each is a `gaawe` tag with an
explicit `measurementIdOverride: G-5NPVYW5V3R` (this container uses the newer
unified "Google Tag" template rather than a classic GA4 Configuration tag, so a
GA4 Event tag needs the measurement ID stated directly — the API rejects the tag
without it), fires on its matching Custom Event trigger, and is blocked by the
same "BLOCK - non-production hostname" trigger (60) every other tag already uses,
so none of this fires on Cloudflare previews or `staging.`/`app.` subdomains.
Event parameters sent to GA4:

| GA4 event | Parameters |
|---|---|
| `cta_click` | `cta_destination`, `cta_location`, `cta_text`, `page_path` |
| `form_start` | `form_id`, `page_path` |
| `form_error` | `form_id`, `field`, `page_path` |
| `form_submit_success` | `form_id`, `page_path` |

### The free-trial CTA, present and future

`src/scripts/track.ts` no longer hardcodes `/book-a-call` as the thing it watches
for. It now matches clicks against `SIGNUP_URL` and `DEMO_URL` from
`src/data/site.ts` directly, and reports which one matched as `cta_destination`
(handling both same-origin destinations, with locale prefixes stripped, and a
future cross-origin destination by exact origin+path). Concretely:

- **Today**, `SIGNUP_URL` and `DEMO_URL` are both `/book-a-call`, so every tracked
  CTA reports `cta_destination: '/book-a-call'`. `cta_location` is still what
  separates the primary "Book a demo" buttons (nav/hero/pricing/footer/content)
  from the one secondary inline link in the FAQ page.
- **The day `SIGNUP_URL` is switched** to the real trial URL (per its comment in
  `site.ts`, expected to be `https://app.hubsell.com/signup`), every primary CTA
  on the site starts reporting `cta_destination: 'https://app.hubsell.com/signup'`
  automatically — no further code change, no GTM change. The FAQ's secondary
  "book a call" link keeps reporting `/book-a-call` since it reads `DEMO_URL`,
  which stays put per CLAUDE.md ("Demo request stays as a secondary conversion").
  This is exactly the split GA4 needs to compare trial-click volume against
  demo-click volume once the trial launches.
- **What this does not cover:** the trial signup itself happens on
  `app.hubsell.com`, a separate application outside this repo. `cta_click` on the
  trial button is trackable here; the actual trial-start completion is not — that
  event, if wanted, has to be instrumented in the app's own codebase/GTM
  container, not this one.
